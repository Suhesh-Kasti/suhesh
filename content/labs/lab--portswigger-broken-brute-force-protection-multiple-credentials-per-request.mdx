# Lab: Broken brute-force protection, multiple credentials per request

This one is short and almost funny. The login endpoint takes JSON, and it is happy to accept an array where it expected a single password. So instead of a thousand requests, you send one, and the server checks your whole wordlist for you.

## The setup

You only need `carlos` as the username. The login form posts credentials as JSON rather than form fields:

```json
{"username":"wiener","password":"peter"}
```

That shape is the tell. A normal form endpoint gives you `username=...&password=...`. This one is built for structured objects, and structured objects can be arrays.

## How the vulnerability works

The brute-force protection here is a cap on the number of requests, not on the number of guesses. The developer assumed one request means one password. If you cannot make many requests, you cannot try many passwords.

Nothing enforces that one-to-one mapping. The server deserialises the password into a string and compares it. If the client sends an array instead, a lenient parser feeds each element to the comparison in turn. Every candidate gets checked inside a single request, so the request cap is counting to one while the server actually guesses a thousand times.

The lab also tells you the password lives in the standard candidate list, so you do not have to be clever about which values to send.

## Solving it

1. Log in with `wiener:peter` and capture the `POST /login` request.
2. Send it to Repeater.
3. Replace the single password string with the full candidate list as a JSON array, and set the username to `carlos`.

```json
{
  "username": "carlos",
  "password": [
    "123456",
    "password",
    "12345678",
    "qwerty"
  ]
}
```

4. Send it. You get a `302`.
5. Right-click the request, choose Show response in browser, copy the URL, and load it. You are logged in as Carlos.
6. Click My account.

## Why that payload works

The server wanted one password and got many. Its request-level rate limiter sees a single login attempt, so the counter stays at one. The credential check itself loops over the array and succeeds as soon as one entry matches. The real password is somewhere in that array, so one request stays under the limit and finds the winner at the same time.

## The fix

Type the input. If the login expects a string, reject anything that is not a string before it reaches the credential check. Never let the rate limiter count requests while the credential check counts guesses, because the two must count the same thing. Run the comparison once per request with exactly one password, and throttle failed attempts against that account.
