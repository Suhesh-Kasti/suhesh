The word "IP block" makes you reach for an `X-Forwarded-For` header and an address rotation. That is a real bypass for some rate limiters. The documented route here is lower-tech: keep the failed-attempt counter under three by logging in as myself every other try.

## The setup

The login page blocks your IP after three wrong passwords in a row. You get a message about too many incorrect attempts, then a timer. You have your own credentials `wiener:peter`, and you want the password for `carlos`.

## How the vulnerability works

The block counts failures from one IP, which sounds fine. The flaw is what resets that count: any successful login from the same IP clears it back to zero.

So the rule is not "three failures per IP". It is "three failures in a row per IP". Slip one good login into the run and you start again with a clean slate. My own account is the reset button, and the app hands it to me for free.

That is why the counter, not the source address, is the thing to attack. The block only matters if failures are allowed to pile up, and I control whether they do.

## Solving it

1. Send `POST /login` to Intruder and pick a Pitchfork attack, with payload positions on both `username` and `password`.
2. In the resource pool, set maximum concurrent requests to `1`. Order matters: the requests must go out one at a time so a success lands between failures.

```text
username payloads: wiener,  carlos, wiener,  carlos, wiener,  carlos, ...
password payloads: peter,   a1,     peter,   a2,     peter,   a3,     ...
```

3. Build the username list so it alternates, with your username first and `carlos` repeated at least a hundred times.
4. Build the password list the same way: your real password before every candidate, kept aligned with the usernames.
5. Start the attack. When it finishes, hide the `200` responses and look for the single `302` on a `carlos` request.

```http
POST /login HTTP/2

username=carlos&password=WINNING-CANDIDATE
```

6. Take that password, log in as Carlos, and open his account page.

## Why that payload works

Pitchfork advances both lists together, so request one is `wiener:peter` (a real login, counter reset) and request two is `carlos:<candidate>` (a guess). The pattern is guess, reset, guess, reset. The failure count never reaches three, so the IP ban never triggers, and the whole candidate list gets tested. Sending one request at a time is what keeps each reset and the next guess in the right order.

## The fix

Rate-limit and lock per account, not per IP, and do not let a success from a shared address wipe the count for a different account. Count failures against the account being targeted and add a delay that grows with the count. If you must block by IP, read the address from the connection rather than from a client-supplied header.
