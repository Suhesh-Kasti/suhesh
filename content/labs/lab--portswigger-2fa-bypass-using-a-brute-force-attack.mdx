# Lab: 2FA bypass using a brute-force attack

They hand you Carlos's password in this one, so the password is not the problem. The 4-digit code is. Two wrong guesses throw you back to the login page, which kills a plain Intruder run, so the fix is to make Burp log you back in between every single guess.

## The setup

Log in as `carlos:montoya` and you land on a page asking for a 4-digit security code. There is no email here. The code is generated fresh and you cannot see it. Two failed codes and the session is gone, so the third request needs a brand-new login.

## How the vulnerability works

Four digits is 10,000 possibilities. That is small. Anywhere that lets you try thousands of values against a short code with no account lockout is brute-forceable, no cleverness required.

The only defence is the two-strikes logout, and it is weak. It is tied to the session, not to the account. Log in again and you get a new session with a fresh budget of two tries. So the block never actually stops anyone, it just costs one extra request per guess.

The code also regenerates while you work. When a new code is minted it may already be a number your run has passed, which is why the attack sometimes has to be repeated.

## Solving it

1. Log in as `carlos:montoya` and reach the 2FA page. Confirm that two wrong codes kick you out.
2. In Burp, open Settings > Sessions > Session Handling Rules and add a rule scoped to all URLs.
3. Add a rule action: Run a macro. Record a macro with three requests:

```http
GET /login
POST /login
GET /login2
```

Test the macro. If the final response is the 4-digit code page, it works.
4. Send `POST /login2` to Intruder and put a payload position on `mfa-code`.

```http
POST /login2 HTTP/2
Cookie: session=YOUR-SESSION

mfa-code=§0000§
```

5. Payload type Numbers, range `0`-`9999`, step `1`, 4 digits.
6. Put the attack in a resource pool with maximum concurrent requests set to `1`, so guesses stay ordered and the macro stays clean.
7. Start it. The request that is not a `200` is the win. Show it in the browser and click My account.

## Why that payload works

Two pieces click together. The macro gives every guess a fresh session, so the two-strike logout never survives to the request that matters. The number payload walks the whole 4-digit space. Neither half is clever, but together they turn a locked door into a 10,000-step loop with an automatic doorman.

## The fix

Lock the account after a small number of failed second-step attempts, and count those attempts server-side per account, not per session. Make a code valid for one attempt and expire it after a few minutes. A 4-digit code with per-account throttling locks out long before 10,000 guesses are worth trying.
