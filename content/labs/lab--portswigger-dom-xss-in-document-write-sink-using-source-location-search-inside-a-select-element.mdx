# Lab: DOM XSS in document.write sink using source location.search inside a select element

The reflection is not in a search box at all. It is in the `storeId` parameter of a product page, written into a `select` you never fill in by hand. I hunted the search parameter for a while before I read the source properly.

## The setup

A product page reads `productId` and `storeId` from the query string. A script pulls `storeId` out of `location.search` and `document.write`s it as the selected option inside a `select` element. So the injection point sits between the opening and closing select tags, as the content of an option, not inside a quoted attribute.

## How the vulnerability works

Same shape as any DOM XSS: `location.search` is the source, `document.write` is the sink, and the value is concatenated into markup with no encoding. What changes is the position. You are not inside a quoted attribute this time, you are inside the document body between `select` and its closing tag. That changes the escape sequence. You do not need a closing quote, you need to close the `select` element first, because a browser drops most markup placed inside a select down to its options and nothing else.

## Solving it

1. View the source of a product page and find the script using `storeId` from `location.search`.
2. Note the context. The value is written as the content of an option inside a select.
3. Close the option and the select, then inject an image with an error handler.
4. Load the product page with both parameters:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/product?productId=1&storeId="></select><img src=1 onerror=alert(1)>
   ```
5. The image fails to load, `onerror` fires, and the alert runs.

## Why that payload works

The value goes into the body of the page, so the `"></select>` part closes the current option and the surrounding select. Once you are outside the select, the browser will happily parse an `img`. The `src=1` is not a real image, so the load fails and `onerror` executes. You need the select closed because browsers discard most markup inside a select; escaping it is what lets the new element survive.

## The fix

Take the store id, validate it against the known list of stores, and set the selection through the DOM instead of building HTML from a string. Encoding alone is not the right answer here, because the value is supposed to be an id, not markup; validate the shape and reject anything that is not one.
