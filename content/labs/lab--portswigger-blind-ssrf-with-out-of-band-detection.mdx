# Lab: Blind SSRF with out-of-band detection

Most SSRF labs pay out with data in the response. This one gives you nothing back. The only proof the server made a request is on a machine you control, which is exactly the problem Burp Collaborator solves. It is a small lab, but the idea behind it shows up everywhere.

## The setup

Analytics software watches the `Referer` header when a product page loads and fetches that URL server-side. The fetched content is never returned to you, so you cannot read it. All you get to see is whether the request happened at all.

## How the vulnerability works

The fetcher takes a request header the client fully controls and makes a server-side request to it, with no allow-list. Because the result is discarded, you cannot pivot to read internal pages, but you can still confirm the request and where it went. Give the server a URL whose DNS and HTTP traffic you can observe, and the observation itself becomes the leak.

## Solving it

1. Open a product page with Burp running, catch the request, and send it to Repeater.
2. Generate a Collaborator payload from the Collaborator tab.
3. Replace the `Referer` value with it:

```http
Referer: https://YOUR-COLLABORATOR-SUBDOMAIN/
```

4. Send the request.
5. Poll Collaborator. You should see a DNS lookup and an HTTP request coming from the back-end.

If nothing shows up, wait a few seconds. The fetch runs asynchronously.

## Why that payload works

The `Referer` value is not validated, so the analytics fetcher resolves whatever host it contains. The Collaborator domain uses name servers Burp controls, so the lookup alone leaks: the server's resolver asks Burp's authoritative server to resolve the name. Then the HTTP fetch lands on Burp's listener. Two interactions, both traceable to the back-end.

The lab firewall blocks arbitrary external hosts on purpose, so only the default public Collaborator server counts here.

## The fix

Never fetch URLs that come from client input. If a feature genuinely needs it, keep an allow-list of exact hosts and schemes, strip inbound headers such as `Referer` and `X-Forwarded-*` before the fetch, and run the fetcher behind an egress proxy that denies private address ranges. Assuming the response stays hidden does not make the request safe.
