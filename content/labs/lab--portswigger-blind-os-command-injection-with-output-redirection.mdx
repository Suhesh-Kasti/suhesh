# Lab: Blind OS command injection with output redirection

Time delays tell you a command ran. This lab is the step where you finally read what it said, and it does it without any external infrastructure. Just a file write into a directory the web server already exposes.

## The setup

Same feedback form, same `email` field, same `/feedback/submit` endpoint, same useless confirmation page. What is new is the pair of facts you can see from outside: the app serves product images from a directory on disk through `GET /image?filename=<name>`, and that directory is writable by the account the web app runs as.

## How the vulnerability works

The shell that runs your injected command can redirect standard output to any file it can write. If a directory it can write to is also served by the web server, the command output becomes an HTTP response. No blind channel needed, because the server will hand you back the file it just wrote.

The shape is: run the command, send its output to a path under the web root, then request that path as though it were an image.

## Solving it

1. Capture the `POST /feedback/submit` request in Burp. The injection point is `email`.
2. Inject a command with a redirection into the images directory:

```
email=x||whoami > /var/www/images/output.txt||
```

3. Send it. This writes the result of `whoami`, the user the app runs as, into a file under the web root.
4. Request that file through the image endpoint:

```
GET /image?filename=output.txt
```

5. Read the response body. It is the command output, retrieved as a normal image request.

`whoami` is just a convenient probe. Any command whose output you want works the same way.

## Why that payload works

The `>` operator truncates the file and writes standard output to the path you name. Because the path is inside `/var/www/images/`, the same directory the image endpoint resolves against, the file is immediately reachable over HTTP with no traversal at all. The `||` again guarantees the base command fails so your command runs, and the trailing `||` closes the construction cleanly.

The cosmetic detail that matters: the file has no image extension, and this image endpoint does not require one, so `filename=output.txt` is served directly.

## The fix

The root cause is unchanged: user input reaching a shell. On top of fixing that, do not serve a directory the application process can write to, and run the process as an unprivileged user with no write access to any web-served path. Least privilege turns a command injection from "read and write anything" into "read and write almost nothing".
