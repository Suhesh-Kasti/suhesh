The two labs on either side of this one trip people in opposite directions, and this is the one where the JavaScript escaping is genuinely solid. The trick is to stop attacking JavaScript and attack HTML instead. Two parsers read your input, and they run in a fixed order.

## The setup

The search query is tracked inside a `<script>` block, roughly `var searchTerms = 'hello';`. Try a single quote and it comes back as `\'`. Try a backslash and it comes back as `\\`. Nothing you can type closes the string. What is not encoded, though, is `<` and `>`. Write those and they pass through clean.

## How the vulnerability works

Your input hits two engines in sequence. The HTML parser runs first. While it reads the contents of a `<script>` element it does not understand JavaScript strings, it is only scanning for the literal sequence `</script>` to know where the script data ends. It does that regardless of whether a quote is open. So the moment your input contains `</script>`, the HTML parser closes the element, and the rest of your input is back in plain HTML land, free to open a brand-new `<script>`. The quote escaping was airtight. It was guarding the wrong layer.

## Solving it

1. Search a test string and view the source to confirm the reflection inside `var searchTerms = '...';`, with quotes and backslashes escaped.
2. Since the escaping lives at the JavaScript level, aim one level up:

```html
</script><script>alert(1)</script>
```

3. Send that as the search term.

The first `</script>` ends the page's own script block. The following `<script>alert(1)</script>` is then read as ordinary HTML and runs.

## Why that payload works

The HTML tokenizer never looks inside a JavaScript string. It sees the characters `</script` and ends the script data immediately, no matter what the JavaScript is doing. After that point you are in HTML context again, which is why you can simply open a new script element. Your escaped quotes stayed escaped and were never the point. You bypassed the JavaScript string entirely by closing the layer above it.

## The fix

Do not interpolate raw data into an inline `<script>`. If you must, JSON-encode the value and also escape the characters that matter to the HTML layer: write `<` as `\u003c` and `/` as `\u002f`, so the byte sequence `</script>` can never appear literally. A Content-Security-Policy without `unsafe-inline` stops the injected script even if the reflection still happens.
