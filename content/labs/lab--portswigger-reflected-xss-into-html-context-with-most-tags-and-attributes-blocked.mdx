# Lab: Reflected XSS into HTML context with most tags and attributes blocked

The WAF on this one blocks most tags and most attributes, which reads like a dead end until you remember that block-lists are never complete. I spent a while guessing bad payloads before I stopped and let Burp Intruder tell me the answer instead.

## The setup

The search box reflects whatever you type straight back into the page with no escaping. The wall in front is a web application firewall: send a `script` tag or a familiar `onclick` and the server returns a 400 "attack detected" page instead of results. The reflection is real, so the only job is finding the tag and the event the block-list forgot.

## How the vulnerability works

Two filters are running, one for the tag name and one for the attribute name. Both are block-lists, so they only reject strings somebody remembered to add. Any tag or event that is not on the list goes through untouched and lands in the HTML unescaped. HTML has well over a hundred tags and as many event handlers, and nobody keeps that list complete.

## Solving it

1. Confirm the reflection. Search for a random string and read the response. It comes back raw, so the sink is fine and only the filter is in the way.
2. Find a surviving tag. Send the request to Intruder, mark the tag name, and fuzz a list of HTML tags.
   ```
   /?search=<§body§>
   ```
   Almost everything comes back 400. `body` does not.
3. Find a surviving event. Same request, but mark the attribute this time.
   ```
   /?search=<body §onresize§=print()>
   ```
   Most events are blocked. `onresize` gets through.
4. The lab forbids user interaction, and `onresize` only fires on a resize. So wrap the payload in an iframe and resize that iframe from its own load handler. Host this on the exploit server:
   ```html
   <iframe src="https://YOUR-LAB-ID.web-security-academy.net/?search=%3Cbody%20onresize%3Dprint%28%29%3E" onload=this.style.width='100px'></iframe>
   ```
5. Store it and deliver to the victim.

## Why that payload works

The inner search term is URL-encoded because it sits inside the iframe `src` attribute. Once the iframe loads, its inline `onload` sets `this.style.width`, which resizes the framed document and fires `onresize` on its `body`. That runs `print()` with no click and no keypress from the victim.

## The fix

Encode the reflected value for its context, so `<` and `>` become entities and there is nothing to break out of. Then add a sanitizer allow-list like DOMPurify and a strict CSP. Blocking more tag names is not a fix; it is the reason this lab exists.
