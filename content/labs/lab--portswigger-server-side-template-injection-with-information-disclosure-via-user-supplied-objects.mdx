# Lab: Server-side template injection with information disclosure via user-supplied objects

The content-manager account lets me edit product templates, which is already a strange amount of power. Those templates render on the server, and that is where this gets interesting.

## The setup

Log in as `content-manager:C0nt3ntM4n4g3r` and open a product description template. You can put template expressions in the text and watch them evaluate when the page renders. That is the injection point. The real question is which engine sits underneath, and which objects the template can reach.

## How the vulnerability works

A template engine renders placeholders and tags on the server before the HTML is sent. If user input is compiled as a template, the user can call whatever the engine exposes. Here an object with sensitive attributes is passed into the template context, so the template can read it. The engine is Django, and Django ships a built-in `debug` tag that dumps every variable and object available in the current context. That tag is the reconnaissance step.

## Solving it

1. Log in and edit a product template. Break it on purpose to make the engine complain:

```
${<%[%'"}}%\
```

The error output names the framework, which is Django.

2. Now ask Django to list what is in scope:

```
{% debug %}
```

Save the template. The output lists the context: variables, filters and objects. The one that matters is `settings`.

3. Django's `settings` object holds framework configuration, including `SECRET_KEY`. Read it directly:

```
{{settings.SECRET_KEY}}
```

4. Save the template. The rendered page prints the key. Click Submit solution and paste it in. The value differs per instance, so take it from your own output.

## Why that payload works

Once input is compiled as a template, any tag or filter the engine exposes is callable. The `debug` tag is not a vulnerability on its own; it is a normal debugging helper that leaks the context when it runs in production. That context includes the `settings` object, and `SECRET_KEY` is a plain attribute read. No code execution is needed, which is the point of the lab: information disclosure through object access, not a full remote code execution chain.

## The fix

Never render user-supplied strings as templates. Treat them as data and pass them into a fixed template, or use an engine that cannot reach framework objects. Switch off debugging helpers like the `debug` tag in production. And keep `SECRET_KEY` out of any context object a template can touch, since the key signs sessions and tokens.
