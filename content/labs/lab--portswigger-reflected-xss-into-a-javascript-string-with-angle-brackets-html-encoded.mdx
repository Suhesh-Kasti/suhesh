This is the mirror image of the lab before it. There, quotes were the wall and angle brackets walked straight through. Here the angle brackets are encoded, so you cannot touch the HTML, and the single quote is sitting there completely unescaped. Same reflection point, opposite door.

## The setup

The search term is reflected in a script block, `var searchTerms = 'test';`. Search for `<script>alert(1)</script>` this time and it comes back HTML-encoded, so tag injection is dead. Send a lone `'` and it is echoed back untouched. The app spent its escaping budget on the HTML layer and left the JavaScript string open.

## How the vulnerability works

Angle-bracket encoding is an HTML defence. It exists to stop your input being parsed as tags. It has no opinion about characters that only mean something to JavaScript, and in a JavaScript string the character that matters most is the single quote that closes it. Because the reflection lands inside `'...'`, a single quote in your input ends the string early and puts you in code position. From there it is normal JavaScript, and the HTML encoder never gets a say.

## Solving it

1. Search a test string and view the source to confirm `var searchTerms = 'test';`.
2. Add a single quote and check that it is reflected raw.
3. Send this as the search term:

```javascript
';alert(1)//
```

4. The `//` comments out the server's trailing `';` so nothing is left dangling.

## Why that payload works

The browser constructs this line:

```javascript
var searchTerms = '';alert(1)//';
```

Your first `'` closes the string, so `searchTerms` is the empty string. The `;` ends that statement. `alert(1)` is now a free-standing expression and runs immediately. The `//` turns the leftover `';` from the page into a comment, which prevents a syntax error. Every character that decided the outcome was invisible to the angle-bracket encoder, because that encoder was watching the wrong context.

## The fix

Escape for the context you are actually in. For a JavaScript string that means escaping `'`, `"`, `\` and line terminators, or better, JSON-encoding the value so no raw quote can appear. HTML-encoding `<` and `>` is right for HTML, but it is not a substitute for JavaScript string escaping, and neither replaces keeping data out of inline scripts altogether.
