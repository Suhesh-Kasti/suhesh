# Lab: Accessing private GraphQL posts

The blog pulls its posts through GraphQL, which is the kind of detail I usually skim past. Here it matters, because a gap in the list of post ids points straight at a post the site does not want me to read.

## The setup

Open the blog and watch the traffic. Posts arrive from `POST /graphql/v1`, and each one has a sequential `id`. When I counted them, id 3 was simply absent: 1, 2, 4, 5 and so on. A hole in a sequential list is a hidden row, every time.

## How the vulnerability works

GraphQL returns exactly the fields the client asks for and nothing else. The developers wrote a query that fetches the title, summary and body for the visible posts, and never mentioned the other fields that exist on the `BlogPost` type. Those fields are still sitting on the server. The type has a `postPassword` field, and introspection will read the schema and hand you its name. Once you know the field exists, you can request it for any post, including the one the UI drops.

The authorization mistake is that the password lives on the same object as the public post data, so nothing stops a query that asks for it.

## Solving it

1. Open a post or the index and find the `POST /graphql/v1` request in your proxy history. Send it to Repeater.
2. Run introspection to read the schema. Look at the `BlogPost` type and note the `postPassword` field.
3. Build a query for the missing id and include that field:

```
POST /graphql/v1
Content-Type: application/json

{
  "query": "query getBlogPost($id: Int!) { getBlogPost(id: $id) { title postPassword } }",
  "variables": { "id": 3 }
}
```

4. The response returns the password for the hidden post. Submit it to solve the lab. The value is unique per instance, so copy it from your own response.

## Why that payload works

GraphQL object types do not hide fields per caller. If a field is part of the type, a query can select it, as long as the resolver returns it. The `postPassword` resolver does no ownership check; it reads the column and returns it. Introspection is the part that turns this from guesswork into a straight lookup, because it names the field for you.

## The fix

A field like `postPassword` should not sit on the type the public query returns. Keep secrets in a separate type with its own authorization, or drop the field entirely. Disable introspection in production. Any resolver that returns sensitive data must also verify that the caller is allowed to see that specific object, not just that they are logged in.
