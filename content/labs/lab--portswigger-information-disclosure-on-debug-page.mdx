This one is nearly all recon. The debug page is not linked in the visible UI anywhere, but a developer left a pointer to it in an HTML comment on the home page. Read the source, follow the breadcrumb, grab the secret.

## The setup

The home page loads normally and looks clean. Buried in its markup is an HTML comment, though, and that comment carries a link to a file that should never have survived deployment.

## How the vulnerability works

A `phpinfo()` page was left reachable after the site went live. It prints the environment the web process runs in, which includes application settings and secrets such as `SECRET_KEY`. The page is a development convenience, and nothing removed it or blocked it once the app was in production.

## Solving it

1. Load the home page and view the source, or use Burp's site map and its "Find comments" tool.
2. Find the comment pointing at the debug file:

```html
<!-- <a href="/cgi-bin/phpinfo.php">Debug</a> -->
```

3. Request that path directly:

```http
GET /cgi-bin/phpinfo.php HTTP/1.1
Host: LAB-ID.web-security-academy.net
```

4. Search the returned page for `SECRET_KEY` and copy the value.
5. Submit the value in the lab's solution box.

## Why that payload works

The comment itself is harmless, but it advertises a path that survived deployment. The server runs the PHP file and renders every environment variable into a tidy table, so the secret is printed in plain text. Nothing restricted the endpoint, so the information is public by default.

## The fix

Strip debug files and `phpinfo()` calls from production builds, and block `/cgi-bin/phpinfo.php` at the edge in case one ships anyway. Keep secrets in a dedicated store rather than in the web process environment, and inject only what the app needs, so a page that dumps the environment has less to dump.
