After all that key recovery, this one feels like cheating. The server takes the verification key straight out of a header field called `jwk`, so I just hand it a key I generated and sign with its private half. I never need the server's key at all. It is a shorter lab than the last two and it teaches a cleaner lesson.

## The setup

Log in as `wiener:peter` and look at the JWT. The header here carries an embedded key:

```json
{"kid": "<some-kid>", "jwk": {"kty": "RSA", "n": "...", "e": "AQAB"}}
```

The `jwk` field is meant as a convenience. The token self-describes which key signed it. That is safe only if the verifier checks that this embedded key is one it already trusts, which is the whole question here.

## How the vulnerability works

A JWK is just a JSON description of a key. JWT Editor can generate a fresh RSA keypair and paste the public half into the header as `jwk`. When the server reads the token, it extracts that public key and uses it to verify the signature. If it never asks whether the key is one of its own, it is verifying the token with a key the attacker chose, which is no verification at all.

The endpoint here only accepts RSA, which is why the injected key has to be an RSA key rather than a symmetric one.

## Solving it

1. Log in as `wiener:peter` and capture the JWT.
2. In JWT Editor generate a new RSA key. The extension holds it as the active signing key.
3. Open the token in the JWT tab and set the payload `sub` to `administrator`.
4. Use Attack, then "Embedded JWK", and confirm the injected key. JWT Editor rewrites the header with your public key in `jwk` and re-signs the token with the matching private half it holds.
5. Send the request, browse to `/admin`, and delete `carlos`.

## Why that payload works

The verifier consults the token to find out how to verify the token. My `jwk` says "use this RSA key", the signature was made with that key's private half, and the check passes. There is no trust anchor anywhere on the path, because the same header the attacker controls supplies both the algorithm and the key. The `kid` is a label pointing at a key the app already has. `jwk` stabs at supplying the key itself, and that is the difference between them.

## The fix

Do not accept a key from the token unless it matches one the server already holds, and ideally do not accept embedded JWKs at all. Keep the verification key set fixed server-side, resolve `kid` inside that trusted set, and reject any token that carries its own key material.

<Accordion title="Why the kid value still matters">
The header also keeps a `kid`. In a sane app that value selects one entry from a fixed server-side key set, and an unknown `kid` is rejected. Here the `jwk` short-circuits that lookup, so the `kid` is along for the ride. When a header carries both, test which one the server actually honours.
