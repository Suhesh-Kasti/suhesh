# Lab: Information disclosure in error messages

There is not much to bypass here. The bug is that the server answers a bad input by dumping its entire stack trace, and the trace cheerfully announces which framework build is running. One broken request and you have the version number.

## The setup

Product pages are fetched with an integer parameter: `GET /product?productId=1`. Any well-formed number returns a product, and there is nothing else to the feature.

## How the vulnerability works

When the parameter cannot be converted to the type the code expects, the framework raises an exception. The app is configured to return that exception to the client, and a Java stack trace is chatty: package names, class names, and the framework version. A version number is not sensitive on its own, but it maps straight onto a list of known vulnerabilities for that exact release.

## Solving it

1. Open a product page and note `productId` in the query string.
2. Send the request to Repeater.
3. Replace the integer with a string:

```http
GET /product?productId="abc" HTTP/1.1
```

4. The response is a 500 with a full stack trace. Read the framework banner in it: Apache Struts 2 2.3.31.
5. Submit `2 2.3.31` in the lab's solution box.

## Why that payload works

The parameter is bound as an integer, so `"abc"` fails conversion and throws inside the framework. The error handler prints the whole chain rather than a generic page, and that chain includes the Struts version string. The disclosure is not the crash. It is the choice to render internal error text to whoever asked.

## The fix

Disable verbose errors in production and return a generic 500 page. Log the trace server-side with a correlation id and show the user only that id, so support can still look it up. Keep dependencies patched, since a leaked version is only interesting when it is old, and avoid advertising the framework in response headers either.
