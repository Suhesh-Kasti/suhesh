# Lab: Reflected XSS into a template literal with angle brackets, single, double quotes, backslash and backticks Unicode-escaped

This lab looks like the most locked-down one in the set: quotes, backslashes, backticks and angle brackets are all escaped. The escape hatch is that it is not a plain string. It is a template literal, and template literals evaluate code inside themselves.

## The setup

Search, and the term comes back inside a template literal. The server builds something like this:

```javascript
var message = `0 search results for 'test'`;
```

Probe the dangerous characters and they come back Unicode-escaped: `<` becomes `\u003c`, `'` becomes `\u0027`, `"` becomes `\u0022`, `\` becomes `\u005c`, and the backtick becomes `\u0060`. Every character you would use to close the string or start a tag is neutralised.

## How the vulnerability works

The context is a template string, not a plain one. Template literals support interpolation: anything between `${` and `}` is evaluated as JavaScript and spliced into the string. The filter escaped the characters needed to break out of the literal, plus the HTML characters. It did not escape `${` and `}`, which are not dangerous syntax for a plain string. In a template literal, they are the injection point.

## Solving it

1. Search a test string and confirm the reflection sits inside the backtick-delimited template literal.
2. Do not try to close the literal. Use the interpolation instead.
3. Send this as the search term:

```javascript
${alert(1)}
```

The response becomes `` var message = `0 search results for '${alert(1)}'`; `` and the expression evaluates when that line runs.

## Why that payload works

When the JavaScript engine reaches `${`, it stops treating the template as literal text, evaluates the expression, and inserts the result. `alert(1)` runs at that moment. The escaped quotes stay harmless, because you never left the literal. The expression ran from inside the string, which a broken-out string or an injected tag cannot do.

## The fix

Escaping a fixed list of characters is whack-a-mole. If user input must reach a template literal, escape the interpolation characters too: `$` becomes `\u0024`. The sturdier fix is to stop building JavaScript from strings. Serialise the data with `JSON.stringify`, put it in a `data-` attribute or a `<script type="application/json">` block, and read it from there. Keep a CSP so inline scripts cannot run.
