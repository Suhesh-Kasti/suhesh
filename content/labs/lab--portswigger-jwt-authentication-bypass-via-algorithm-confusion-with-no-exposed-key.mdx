This is the previous confusion lab with one new obstacle in front of it: the public key is not published anywhere. It is the hardest of the set for me, mostly because the recovery step uses a tool I had never touched. Once the key is out, the rest is copy-paste from the last lab.

## The setup

Log in as `wiener:peter`. The header is `RS256` again, but this time there is no `/jwks.json` and no key served to the browser, so the fetch step from before comes up empty. The server still holds the key and still signs tokens with it, deterministically. That is the crack in the door: I can get two different messages signed under the same key.

## How the vulnerability works

RSA signatures carry a structure you can exploit once you hold two of them from the same key. With the modulus `n` and exponent `e` unknown, two signatures over known messages and their padding give enough algebra to solve for `n`. That is the whole idea behind the `rsa_sign2n` recipe and its `sig2n` tool. It is not breaking RSA, it is recovering the public parameters from public signatures.

Once I have `n` and `e` I can build the public key. And once I have the public key, the confusion from the previous lab applies unchanged: ask the server to verify HS256 and use those public bytes as the HMAC secret.

## Solving it

1. Log in and grab two JWTs for the same account. Take one, then force a fresh one so a claim like `exp` differs. Differing payloads are what the recovery needs.
2. Run the key-recovery tool over the two tokens:

```bash
docker run --rm -it portswigger/sig2n <token1> <token2>
```

3. It prints candidate values for `n` and `e`. Try the first candidate against the target; if the token is rejected, try the next one, because the tool cannot be sure which candidate is the real modulus.
4. Build the RSA public key from the recovered values in JWT Editor and convert it to PEM.
5. Change the payload `sub` to `administrator`, set the header to `HS256`, and sign with the public key as the HMAC secret.
6. Send, open `/admin`, and delete `carlos`.

## Why that payload works

Two signatures under one key leak the modulus, because the algebra ties them together through the padding scheme. Reconstruct that modulus and the public key is no longer secret even though nobody published it. From there it is the same flaw as before: the server reads the algorithm from the token and, told HS256, uses its RSA public key as a shared HMAC secret.

## The fix

Fix the algorithm server-side and refuse tokens that name a different one, which defeats both this and the exposed-key version. Keep asymmetric and symmetric keys strictly separate. Publishing the public key is normal; what is fatal is letting it double as an HMAC secret.
