I went down a wrong path on this one for a good while. I kept trying to guess the front-end header and kept missing it, when the server was willing to hand it over the whole time.

## The setup

The admin panel lives at `/admin`. Visit it and you get a message saying the panel is only for administrators, or for requests coming from a local IP. That second half is unusual and worth remembering. The product page is where the header shows up, and it is the piece that makes the bypass work.

## How the vulnerability works

A front-end proxy often stamps every request with the client's IP address so the back end can trust it. Here that header is `X-Custom-IP-Authorization`, and the back end has decided that any request carrying `127.0.0.1` came from the machine itself. The flaw is that the header is trusted as-is: if a client can set it, the client controls the "local IP" decision. The server also reflects request headers, which is how you learn the name in the first place.

## Solving it

1. Browse to `/admin` and note the message: administrators only, or a local IP. You now know the bypass is IP-based.
2. The `TRACE` method echoes the request back. Send it against the product page:

```
TRACE /product?productId=1 HTTP/1.1
Host: LAB
```

The response includes an `X-Custom-IP-Authorization` header carrying your own IP. That is the header the front end adds.

3. Add that header to your requests, claiming to be local:

```
X-Custom-IP-Authorization: 127.0.0.1
```

In Burp, add a Match and Replace rule of the request-header type so every request gets it automatically. A single manual request works too, but the admin panel loads several resources, so the rule saves effort.

4. Reload the site and open the admin panel. Delete `carlos`.

## Why that payload works

The back end looks for the header and compares its value to `127.0.0.1`. It never checks that the header came from the proxy rather than the client. Reusing `TRACE` is what turns the lab from guesswork into a lookup, because the server reflects the header back and names it for you. Once you know the name and the value the back end trusts, the bypass is trivial.

## The fix

The back end should not trust a client-controllable header for an IP check. If a proxy must pass the real IP, strip any client-supplied copy of that header at the edge and only accept the proxy's own addition. Better still, do not gate authorization on source IP at all; check the session and the user's role on the server. Turn `TRACE` off in production.
