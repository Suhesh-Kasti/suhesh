Nobody rate-limits a password change form, because why would they. This one carries a hidden `username` field, and its errors split into two reasons: a wrong current password, or two new passwords that disagree. The gap between those two messages is a password oracle.

## The setup

Log in as `wiener:peter`, open the change-password page, and submit the form. The body looks like this:

```text
username=wiener&current-password=peter&new-password-1=...&new-password-2=...
```

The username is a hidden field you can edit. The form wants the current password, then two copies of the new one.

## How the vulnerability works

There are three cases to watch.

- Wrong current password, two new passwords that match: the account is locked. Avoid this one.
- Wrong current password, two new passwords that differ: you get `Current password is incorrect`.
- Correct current password, two new passwords that differ: you get `New passwords do not match`.

The messages differ depending on whether the current password was right, and they differ even when the new passwords do not match. That means the server checks the current password before it complains about the mismatch, and then tells you which check failed. That is a clean yes/no answer on a credential that should not have one.

## Solving it

1. Log in, open the change-password page, and submit the correct current password with two different new passwords. Confirm you get `New passwords do not match`.
2. Send the `POST /my-account/change-password` request to Intruder.
3. Set the hidden `username` to `carlos`, put a payload position on `current-password`, and make sure the two new-password values differ from each other.

```http
POST /my-account/change-password HTTP/2
Cookie: session=YOUR-SESSION
Content-Type: application/x-www-form-urlencoded

username=carlos&current-password=§candidate§&new-password-1=aaa&new-password-2=bbb
```

4. Load the candidate password list as the payload set.
5. Add a grep match rule for `New passwords do not match`. Start the attack.
6. Exactly one response matches. That candidate is Carlos's current password.
7. Log out, log in as `carlos` with it, and open My account.

## Why that payload works

Two different new passwords force the mismatch branch to run, so the only thing between the request and the `New passwords do not match` message is the current-password check. When the current password is right, that check passes and the code reaches the mismatch message. When it is wrong, `Current password is incorrect` fires first and the mismatch message never appears. One string in the response tells you which happened, and a wrong current password with mismatched new passwords does not lock the account, so you can do it for the whole list.

## The fix

Do not leak which check failed. Return one generic error for any failed change, and only after the account is verified. Never trust a hidden `username` field; take the user from the session. And put the same rate limiting and lockout on this endpoint that you use on login, because a password change is a login by another name.
