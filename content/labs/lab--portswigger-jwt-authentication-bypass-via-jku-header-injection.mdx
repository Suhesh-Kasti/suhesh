This is the jwk lab's cousin with one extra hop of indirection. Instead of putting my key inside the token, I put it on a web page and make the token point at that page. It is the same trust bug, dressed up as a key-set reference. Two labs ago I recovered a key I was not given. Here I just publish my own.

## The setup

Log in and inspect the JWT. The header has a `jku` field holding a URL:

```json
{"alg": "RS256", "jku": "https://<lab-host>/.well-known/jwks.json"}
```

A `jku` is a URL pointing at a JWKS document, the same kind of key-set file the algorithm confusion labs fetched. The app loads keys from whatever URL the token names, which is the part that should never be true of attacker-supplied input.

## How the vulnerability works

The flaw is that the URL comes from the token. It should be a fixed address the server controls, but here it is data the attacker can set, so it can point anywhere the server is able to reach. The server then fetches my document, reads my key, and verifies my signature with it.

The lab gives me an exploit server for exactly this. I upload a JWKS file holding the public half of a keypair I generated, set `jku` to that file's URL, and sign with the private half.

## Solving it

1. Log in as `wiener:peter` and capture the JWT.
2. In JWT Editor generate a new RSA keypair.
3. Copy the public key as a JWK, then on the exploit server build a JWKS file around it:

```json
{"keys": [ {"kty": "RSA", "e": "AQAB", "use": "sig", "kid": "<your-kid>", "n": "<your-modulus>"} ]}
```

   Set that file's content type to `application/json` and store it.
4. Edit the token. Set the payload `sub` to `administrator`, set the header `jku` to the exploit server URL of your JWKS, set `kid` to the same `<your-kid>`, and sign with your private key.
5. Send, browse to `/admin`, and delete `carlos`.

## Why that payload works

The verifier trusts a key that arrived by URL and never checks that URL against an allow-list. My JWKS is served by a host I control, so the key it returns is mine, and the signature I made with the matching private key validates. It lands the same way as the jwk lab, one hop further out. Inline key versus remote key is only a difference in where the attacker's key lives.

## The fix

Never take the key-set URL from the token. Pin verification to a server-configured JWKS address and ignore any `jku` the client sends, or validate it against a strict allow-list. Cache the trusted key set and reject tokens whose `jku` is not on it.
