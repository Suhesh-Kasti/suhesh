# How a half proxy works

In a **half proxy** setup the load balancer intercepts the client's request and forwards it to the server, but the response **bypasses the load balancer** and goes straight back to the client. It buys performance in the right setup, and it drags in one big problem: asymmetric routing.

## Asymmetric routing

When traffic takes **different paths** on the way to and from the client, that is asymmetric routing. Network devices like firewalls and routers may discard those packets, because they expect both directions to follow the same route.

1. **Request path:** Client → Load Balancer → Server
2. **Response path:** Server → Client (bypassing the load balancer)

**Why would the packet be discarded?**

- Firewalls and NAT devices keep a connection table tying request and response packets together. If the response comes back on a different path, it doesn't match the table entry, so the device drops it.

## Direct Server Return

A more optimised version of the half proxy is Direct Server Return (DSR). The server replies directly to the client, but only under specific conditions:

- The load balancer forwards the request **without altering** the Layer 3 information (the IPs), but **may rewrite Layer 2** (the MAC addresses).
- The load balancer and the server must sit in the same Layer 2 domain.
- The server must answer the client directly, using the client's IP as the destination, without changing the VIP.

### Example

Let's take:

1. **Client IP:** `192.168.1.10`
2. **Load Balancer VIP (Virtual IP):** `192.168.2.1`
3. **Server IP:** `192.168.3.5`

### Step by step

1. **Client sends a request to the Load Balancer:**
   - Source IP: `192.168.1.10`
   - Destination IP: `192.168.2.1` (the VIP)
2. **Load Balancer forwards it to the Server:**
   - It leaves the IP header untouched, keeping the original source and destination IPs.
   - It rewrites the Layer 2 MAC address so the server actually receives the frame.
   - Source IP: `192.168.1.10`, Destination IP: `192.168.2.1` (the VIP).
   - The server processes it because it recognises the VIP as one of its own addresses.
3. **Server responds directly to the Client:**
   - Instead of going back through the load balancer, it answers the client directly.
   - Source IP: `192.168.3.5`, Destination IP: `192.168.1.10`.

The response never touches the load balancer, which is the whole point: less work on the return path.

## The how and why

### Why does the server accept the VIP as its own?

In DSR the VIP (`192.168.2.1`) is configured on the server too, usually as a loopback or secondary address. When the forwarded packet arrives with the VIP as its destination, the server sees an address it owns and accepts it.

- **VIP on the server:** the VIP is assigned to the load balancer to receive client traffic, and also configured on the server, often on `lo:0`.
- **Using it:** the packet arrives with the VIP as the destination IP, and the loopback address makes the server treat it as local.
- **Responding:** the server replies from the VIP but sends the packet straight to the client, not back through the balancer.

### Why does the client accept the response?

The client only checks the **source IP**. If the response's source matches the VIP it originally asked (`192.168.2.1`), it looks legitimate. The server makes sure the response carries the VIP as its source, so the client believes it is still talking to the VIP, not the real server (`192.168.3.5`).

The server's real IP is only used between the balancer and the server. The client never sees it.

### Can I use this to impersonate another service or MITM?

No. It sounds similar to replying as someone else with a loopback address, but it doesn't work that way.

<Accordion title="Why spoofing with a loopback address fails" color="#ff1144">

1. **Routing.** In DSR the balancer controls the first hop and delivers the client's request to the server. Assigning a public IP (say, Google's) to your loopback doesn't make the internet route Google's traffic to you. Global routing still sends it to the real owner.
2. **Anti-spoofing.** If you reply from an address you don't own, routers and firewalls drop the packet. ISPs block traffic that claims to originate from public ranges you don't control.
3. **No real MITM.** To spoof another service you'd have to intercept requests meant for it, which needs access to a network path you don't have.
4. **TLS.** Even if you intercepted the request, you wouldn't hold the private key. HTTPS traffic is encrypted and the client rejects a response it can't validate.
5. **IP Source Guard and uRPF.** Many networks check that a packet's source matches the interface or path it arrived on, and drop spoofed ones.

</Accordion>
