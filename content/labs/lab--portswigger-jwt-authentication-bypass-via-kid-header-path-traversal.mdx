# Lab: JWT authentication bypass via kid header path traversal

The last lab in the set takes the key reference and turns it into a filesystem path. Instead of abusing which key I get, I make the app read a file that happens to be empty, then sign with nothing. An empty string is a valid HMAC secret, which is the joke at the bottom of this whole series.

## The setup

Log in as `wiener:peter` and inspect the header:

```json
{"kid": "<some-kid>", "alg": "HS256"}
```

On its own, the `kid`, key id, is harmless. It is just a label. But this app resolves it by dropping it into a path and reading that file as the key, something like `keys/<kid>` on disk. The label is going into a file read, and that is the seam.

## How the vulnerability works

Because `kid` is joined into a path and never validated, I can put `../` sequences in it. That lets me steer the read almost anywhere, but I do not want a secret file. I want a predictable one, and `/dev/null` is exactly that: it always reads back as an empty string.

An empty HMAC secret is still a secret the server will use. I know it is empty, so I can sign my forged token with an empty key and the tag will match.

## Solving it

1. Log in as `wiener:peter` and capture the JWT.
2. Change the payload `sub` to `administrator`.
3. Set `kid` to a traversal that lands on null:

```json
{"kid": "../../../../../../../dev/null", "alg": "HS256"}
```

4. In JWT Editor, create a new symmetric key and set its value to an empty string.
5. Sign the token with that empty key using HS256.
6. Send the request, browse to `/admin`, and delete `carlos`.

## Why that payload works

The server takes my `kid`, walks the path, and reads `/dev/null`, which yields zero bytes. Those zero bytes become the verification key. My token was signed with an empty HMAC key, so the computed tag matches and the check passes. The traversal is the delivery mechanism, the empty key is the payload. Adding more `../` than the depth of the key directory is the safe move, since extra traversal just stays at the root.

## The fix

Never build a filesystem path from a token header. Look up `kid` in a fixed in-memory map of known key ids to keys, and reject anything that is not an exact match. As defence in depth, refuse any `kid` containing path separators or traversal sequences. A key file that reads back empty should also be a hard error, not a usable secret.
