I encoded the traversal once, sent it, and got the same rejection as the plain version. That cost me a few minutes. The clue is in the lab name: there is a URL-decode happening that should not be there, and it runs in the wrong place.

## The setup

Same image endpoint, same `filename` parameter. A normal image loads. A plain `../../../etc/passwd` is stripped. A single-encoded `..%2f..%2f..%2fetc/passwd` is also stripped, which is the unusual part. It means the server is decoding the parameter before it checks it.

## How the vulnerability works

The parameter gets URL-decoded when the request is parsed, the result is checked for traversal sequences, and then the value is decoded a second time before it is used on disk. That second decode is superfluous: it does nothing useful for the application, and it hands the attacker a way around the filter.

The filter therefore only ever sees a half-decoded string. Hand it input that holds no traversal at that moment but produces one on the next decode, and it waves the request through.

## Solving it

1. Confirm the double-decode by sending `..%2f..%2f..%2fetc/passwd` and watching it fail. The first decode already produced `../` for the filter to remove.
2. Encode every character of `../` twice. A dot becomes `%2e`, then `%25%32%65`. A slash becomes `%2f`, then `%25%32%66`. Three blocks, then the target:

```
filename=%25%32%65%25%32%65%25%32%66%25%32%65%25%32%65%25%32%66%25%32%65%25%32%65%25%32%66etc/passwd
```

3. Send it. The response is the contents of `/etc/passwd`.

## Why that payload works

Walk the decodes. The first decode of the payload gives `%2e%2e%2f%2e%2e%2f%2e%2e%2fetc/passwd`. The filter checks that string for `../` and finds none, because the dots and the slashes are each still hiding behind a percent sign. The request passes untouched.

Then the second decode runs, the percent signs resolve, and the value becomes `../../../etc/passwd` after the filter has already finished. Three blocks climb from the image directory to root, and `etc/passwd` follows.

The important point: the filter is not weak because it missed an encoding. It is weak because it inspects a string that is about to change.

## The fix

Decode user input exactly once, then canonicalise the resolved path against the media directory and check that the result is inside it. Do not filter a string that still has a decode queued behind it. Same `realpath` plus prefix check as any traversal fix.

<Accordion title="The shorter form people use">
`%252e%252e%252f` means the same thing, written by encoding only the percent sign of each character instead of every character. It decodes once to `%2e%2e%2f` and again to `../`. Both forms are identical to the server. Pick whichever you can type without making a mistake, because one wrong character here fails silently and looks like the bypass does not work.
</Accordion>
