Of the traversal labs, this is the filter I would actually defend in a code review, because "the path must start with the images directory" sounds airtight. It is not, and the reason is worth remembering: a prefix check validates a string, and the kernel validates a path.

## The setup

The image endpoint now wants the full path, not a bare filename. A request with just `49.jpg` fails. The accepted shape looks like this:

```
GET /image?filename=/var/www/images/49.jpg HTTP/1.1
Host: LAB-ID.web-security-academy.net
```

So the app checks that the supplied value starts with `/var/www/images/` and rejects it otherwise. That check is genuinely enforced. Try any other prefix and it fails.

## How the vulnerability works

A start-of-path check confirms where the string begins. It says nothing about where the path ends up. Traversal characters later in the string are still processed by the filesystem when the file is opened, and they are still permitted by the check.

So a value that starts with the required prefix can still resolve to something completely outside the images directory.

## Solving it

1. Send a valid request and note the exact prefix the app requires: `/var/www/images/`.
2. Keep that prefix, then append traversal and the target file:

```
filename=/var/www/images/../../../etc/passwd
```

3. Send it. The response is `/etc/passwd`.

The value passes the prefix check because the first characters are exactly what the app demanded. Everything after them is the escape.

## Why that payload works

The validator runs something like `if not filename.startswith('/var/www/images/'): reject()`. The string `/var/www/images/../../../etc/passwd` starts with `/var/www/images/`, so the test passes and the code moves on. The rest of the string, `../../../etc/passwd`, is then resolved by the operating system relative to `/var/www/images/`: three levels up lands at root, and `etc/passwd` is read from there.

Two different parsers looked at the same string. The application checked its first characters. The kernel walked the whole thing.

## The fix

Canonicalise before validating. `os.path.realpath('/var/www/images/../../../etc/passwd')` collapses to `/etc/passwd`, which does not start with the media directory, so it is rejected, correctly this time. Do the check on the resolved path, and reject any input that is not already a safe relative name.
