`POST` was blocked. The exact same action over `GET` was not. That is the entire lab, and it is a good reminder that an access rule is only as wide as the surface it covers.

## The setup

Log in as `administrator:admin`, open the admin panel, and promote `carlos`. The request that does it is `POST /admin-roles?username=carlos&action=upgrade`. Note where the action lives: in the query string, not the body. The only thing that changes between users is whose session cookie rides along.

The lab then asks me to do the same promotion as `wiener:peter`.

## How the vulnerability works

The access rule is keyed to the HTTP method. The guard on `/admin-roles` only inspects `POST` requests, so a non-admin sending `POST` gets "Unauthorized". The check lives in a routing rule out in front, not in the handler that actually changes the role.

Because the rule is method-scoped, the backend route is still reachable under other methods. Send the same request as `GET` and it never trips the guard, yet the backend processes it and performs the upgrade all the same.

## Solving it

1. As admin, promote `carlos` and send the request to Repeater. It is `POST /admin-roles?username=carlos&action=upgrade`.
2. Log in as `wiener:peter` in a second browser, copy that session cookie into the Repeater request, and send. The response says "Unauthorized".
3. Change the method from `POST` to `POSTX`. The response becomes "missing parameter", which shows the method is exactly where the check sits.
4. Right-click and choose "Change request method" to convert it to `GET`. Change `username` to `wiener`.

```http
GET /admin-roles?username=wiener&action=upgrade HTTP/1.1
Host: <lab-id>.web-security-academy.net
Cookie: session=<wiener-session>
```

5. Send it. A `302` comes back, and `wiener` is now an administrator.

## Why that payload works

The proxy allowed `GET` through because the rule only matched `POST`. The backend, meanwhile, does not care how the request arrived, as long as the parameters are present, so the upgrade runs. Two layers disagree about which requests are sensitive, and the weaker interpretation wins.

## The fix

Put the role check inside the handler that changes the role, and run it for every method that can reach that handler. Access control belongs next to the action it protects, not in a routing rule that keys off the verb. Failing that, reject all methods except the one the endpoint is meant to serve.
