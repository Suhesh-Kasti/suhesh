# Lab: Reflected XSS into HTML context with all tags blocked except custom ones

A filter that rejects every standard HTML tag and then quietly allows the ones it has never heard of is my favourite kind of broken. It took one detour into the idea that custom elements are somehow safe before I just tried one.

## The setup

The search parameter lands in the page unescaped, same as any plain reflected XSS. The difference is the filter: `script`, `img`, `svg`, every common tag returns a 400 or gets stripped out. What survives is any element with a dash in its name, because the developer whitelisted custom elements as harmless.

## How the vulnerability works

Custom elements are just tag names the browser accepts without complaint. They carry no built-in behaviour of their own, which is exactly why the filter trusted them. But global attributes still apply to them. An unknown `<xss>` element can carry `tabindex`, `autofocus`, and `onfocus` like any other element. The browser will focus it, and the focus handler runs. The tag being unknown changed nothing about that.

## Solving it

1. Confirm a normal tag is blocked. Search `<script>alert(1)</script>` and watch the request get rejected.
2. Confirm a custom tag is allowed. Search for `<xss>` and see it reflect intact.
3. Give the custom element a way to focus itself and an action to run on focus.
   ```
   <xss autofocus tabindex=1 onfocus=alert(document.cookie)></xss>
   ```
4. The lab wants no user interaction. `autofocus` makes the element grab focus on load, so `onfocus` fires by itself.
5. Bounce the victim to the injected URL. Since the payload lives in the query string, the simplest delivery is a redirect from the exploit server:
   ```html
   <script>
   location = 'https://YOUR-LAB-ID.web-security-academy.net/?search=%3Cxss+autofocus+tabindex%3D1+onfocus%3Dalert%28document.cookie%29%3E%3C%2Fxss%3E'
   </script>
   ```
   Store it, then deliver it to the victim.

## Why that payload works

`autofocus` is applied the moment the element enters the DOM, and focusing an element fires `focus`, which the inline `onfocus` catches. The custom tag name slips past a filter that only lists known-dangerous tags, and none of the attribute names are on the block-list either. The unknown tag is doing the work, not some parser quirk.

## The fix

Escape the output for the HTML context so the angle brackets never form an element in the first place. If user markup is truly required, run it through a sanitizer that allow-lists specific tags and attributes. Never treat an unknown tag as safe by default; unknown today is a valid element tomorrow.

<Accordion title="Why not use the classic onmouseover?">
Because the lab forbids user interaction. `onmouseover` needs the victim to move a mouse over the element, and the simulated victim never does. `autofocus` plus `onfocus` is the shortest route to a handler that fires on its own, and it survives a filter that never listed those attributes.
