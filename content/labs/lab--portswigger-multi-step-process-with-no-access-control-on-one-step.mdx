The first step of the role change checked who I was. The last step did not. All the protection sat on the doorway and none of it on the switch.

## The setup

Log in as `administrator:admin` and promote `carlos`. This time the promotion is a two-step flow. The first request is `POST /admin-roles` with `username=carlos&action=upgrade`, and it does not apply anything, it returns a confirmation form. Confirming sends a second `POST /admin-roles`, this one with `username=carlos&action=upgrade&confirmed=true`, and that is what actually changes the role.

## How the vulnerability works

The gate is on step one. The selection request is checked for admin rights, which is why a non-admin hitting it gets a `401`. Step two, the request that commits the change, assumes the earlier step already passed and never repeats the check. It trusts a single parameter, `confirmed=true`, as proof that an authorised user clicked through.

I can send that commit request myself. My session is wiener's, the request carries `confirmed=true`, and the handler has no reason to doubt it, so the upgrade goes through without any admin ever touching it.

## Solving it

1. As admin, promote `carlos`. The first `POST /admin-roles` returns the confirmation page.
2. Click yes to confirm and capture the second request, the one with `confirmed=true`. Send it to Repeater.
3. Log in as `wiener:peter`, copy the session cookie into that second request, and change `username` to `wiener`.

```http
POST /admin-roles HTTP/1.1
Host: <lab-id>.web-security-academy.net
Cookie: session=<wiener-session>
Content-Type: application/x-www-form-urlencoded

username=wiener&action=upgrade&confirmed=true
```

4. Send it. A `302` comes back and `wiener` is an administrator now.

For contrast, replaying step one as wiener returns `401`. Same cookie, same handler path, only the missing `confirmed` flag and the step change the outcome.

## Why that payload works

`confirmed=true` is client-supplied state standing in for a server-side fact. The commit handler treats it as evidence that a verified user already approved the change, but nothing binds that flag to my session. The workflow's integrity rested on a value I control, so skipping the protected step costs nothing.

## The fix

Re-check the caller's role in the handler that commits the change, not only in the step that starts it. Tie workflow state to the session on the server, so a confirmation is a recorded server-side fact rather than a flag the client can invent. Every step that changes state gets its own authorization check.
