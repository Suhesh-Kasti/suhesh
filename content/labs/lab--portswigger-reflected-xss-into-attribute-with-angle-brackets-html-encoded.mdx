# Lab: Reflected XSS into attribute with angle brackets HTML-encoded

My first thought on this one was that encoded angle brackets meant XSS was off the table, which is wrong in a way that keeps catching me out. The value is reflected inside an attribute, and attribute context has its own escape character: the double quote. That one is left wide open.

## The setup

The search box reflects your term in two places, once in an `<h1>` and once inside the `value="..."` attribute of the search `<input>`. A quick `<script>alert(1)</script>` comes back as `&lt;script&gt;`, so the angle brackets are handled. Send a single `"` on its own, though, and it survives untouched. You have fallen out of the attribute.

## How the vulnerability works

Encoding `<` and `>` stops you creating new tags, but it does nothing about the quote that delimits the attribute you are already inside. If `"` is not encoded, you close `value` early and start adding your own attributes to the existing `<input>` element. You are not building a new tag. You are decorating the one the developer already made, which is why the angle-bracket filter never sees anything to block.

The second problem is triggering execution without a click. An injected `onmouseover` needs a human to move the mouse. Adding `autofocus` to the input makes the browser focus it on load, and `onfocus` fires by itself.

## Solving it

1. Search for a random string and view the response, then note the reflection inside `value="..."`.
2. Confirm that a lone double quote is not encoded.
3. Enter this into the search box:

```html
" autofocus onfocus=alert(1) x="
```

The leading `"` closes `value="`, `autofocus` plus `onfocus` runs the alert on load, and the trailing `x="` swallows the server's own closing quote so the tag stays valid.

## Why that payload works

Walk through the parser. Your first `"` terminates the `value` attribute. The browser then reads `autofocus` and `onfocus=alert(1)` as new attributes of the same `<input>`. `autofocus` tells it to place focus on that field as soon as the document loads, and focusing fires `onfocus`, so the code runs with no user action. The final `x="` ate the quote the page appends, leaving a tidy `x=""` behind instead of a dangling half-tag.

## The fix

Encode quotes as `&quot;` whenever data lands inside an attribute value, and preferably attribute-encode the whole value. A template engine with contextual auto-escaping handles this. On top of that, a Content-Security-Policy that forbids inline event handlers means an injected `onfocus=` never runs, even if the quote slips through.
