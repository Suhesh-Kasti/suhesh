# Lab: Insecure direct object references

Mine is the second chat transcript. That number on its own tells you a first one has to exist, and that is really the whole bug.

## The setup

The site has a Live chat tab. I send a message, click "View transcript", and it downloads a plain text file. The URL is `/download-transcript/2.txt`. A static file, served straight off disk, named with an incrementing number. The transcript endpoint does not even ask me to log in, which already suggests ownership was never part of its design.

## How the vulnerability works

The transcript is fetched by filename, and the filename is a sequential integer. Nothing ties number 2 to my session, and nothing stops me asking for number 1. Whoever owns transcript 1 is a different user, and their file is one decrement away. Because the numbers are small and dense, the whole range is walkable by hand in seconds, no tooling required.

This is a direct object reference: the parameter points at the stored object itself. It is not a case of broken login, because I am not logged in at all here. It is broken authorization, or rather no authorization, on a resource that was never meant to be public.

## Solving it

1. Open the Live chat tab and send a message.
2. Click "View transcript" and download your own transcript.
3. Look at the download URL: `/download-transcript/2.txt`.
4. Change the number to reach the other file:

```http
GET /download-transcript/1.txt HTTP/1.1
Host: <lab-id>.web-security-academy.net
```

5. Read the text. It contains a password for the user `carlos`.
6. Return to the login page and sign in with those credentials.

## Why that payload works

The handler resolves the path to a file on the filesystem and returns its contents. File 1 exists, the web server can read it, and nobody checks whether the requester should have it. A predictable name turns a guess into a hit on the first try.

## The fix

Serve transcripts through an authenticated handler that confirms the file belongs to the current session before returning it, and reference them by an indirect token that maps to the real file on the server. Do not expose the raw filename, and never depend on the number being hard to guess.
