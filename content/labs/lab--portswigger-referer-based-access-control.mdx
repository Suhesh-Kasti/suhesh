The server decided I was an administrator by reading a header my browser writes for me. That is a strange sentence to type, but here we are.

## The setup

The endpoint `/admin-roles?username=carlos&action=upgrade` performs the promotion. When a real admin clicks the button on the admin panel, the browser attaches `Referer: https://<lab-id>.web-security-academy.net/admin`, because that is the page the request came from. As `wiener:peter`, if I browse straight to that URL, my browser sends no Referer and the request is treated as unauthorized.

## How the vulnerability works

The access rule is one line: if the Referer contains `/admin`, allow the request. There is no session role check behind it. The Referer header is set by the browser from wherever you navigated from, and in a proxy like Burp I can set it to any value I like. So the "proof" that I came from the admin page is a string I fully control.

It is worse than forgeable. Referer is not even sent when you type a URL, and privacy settings can strip it. The control manages to be both spoofable and unreliable in normal use.

## Solving it

1. As admin, promote `carlos` and send the request to Repeater. Note `Referer: .../admin` in the request.
2. Log in as `wiener:peter`, and browse to `/admin-roles?username=carlos&action=upgrade`. It is rejected, because no Referer went with it.
3. Copy wiener's session cookie into the captured admin request, change `username` to `wiener`, and keep the `Referer: .../admin` header.

```http
GET /admin-roles?username=wiener&action=upgrade HTTP/1.1
Host: <lab-id>.web-security-academy.net
Cookie: session=<wiener-session>
Referer: https://<lab-id>.web-security-academy.net/admin
```

4. Replay it. A `302` comes back and `wiener` is now an administrator.

## Why that payload works

The check asks where the request appeared to come from, and a header answers that question. Since headers are written by the client, I supply the answer the server wants. The backend then performs the promotion because the condition it tested for was satisfied, even though no admin and no admin password was involved.

## The fix

Authorise on the session's role, server-side, on the request that changes the role. Never use the Referer header as an access decision, it is attacker-controlled and absent more often than people expect. If the concern is cross-site request forgery, that is a real problem, but the answer is a CSRF token bound to the session, not a header the attacker can set.
