The first blind lab I did gave me exactly one bit per request: a `Welcome back` line that is either there or not. No rows, no version banner, no error text. You build the password one character at a time and learn to trust a very small signal.

## The setup

A `TrackingId` cookie again, run through a query on every request. Nothing from that query is printed. But the page shows `Welcome back` only when the query returns at least one row. So a condition I can flip true or false becomes a one-bit oracle.

## How the vulnerability works

The cookie is concatenated into a quoted string in the query. I close the string and add my own boolean condition with `AND`. When the condition is true the query returns a row, so `Welcome back` renders. When it is false the row set is empty and the text disappears. That is a boolean oracle, and a boolean oracle plus patience equals data. Nothing about the result is shown, but the truth value of my condition leaks all the same.

## Solving it

1. Confirm the oracle. True keeps the message, false removes it:

   ```
   TrackingId=xyz' AND '1'='1
   TrackingId=xyz' AND '1'='2
   ```

2. Confirm the table and user exist by making a condition that only holds when a row can be selected:

   ```
   TrackingId=xyz' AND (SELECT 'a' FROM users WHERE username='administrator')='a
   ```

3. Find the password length. Raise the number until the message vanishes:

   ```
   TrackingId=xyz' AND (SELECT 'a' FROM users WHERE username='administrator' AND LENGTH(password)>1)='a
   ```

   It turns out to be 20, but measure it rather than trust it.

4. Extract each character. Send the request to Intruder, mark the final `a`, run the payloads a-z and 0-9, and grep-match `Welcome back`:

   ```
   TrackingId=xyz' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='administrator')='a
   ```

5. The payload on the row that still shows `Welcome back` is the character. Move the offset from 1 to 2, 3 and on until the password is complete.

6. Log in as `administrator`.

## Why that payload works

The condition steers the query between two states that look totally different to the page: rows returned, or none. `SUBSTRING(password,1,1)` slices out a single character, and I test it against one candidate. The candidate is the only thing that changes between requests, so the response flips exactly when I guess right. The `'1'='1` and `LENGTH` checks are the same idea applied to a constant and a length. Every request here is just a yes-or-no question put to the database.

## The fix

Bind the cookie so the quote closes nothing. The deeper point is that a boolean oracle leaks data even when no data is returned, so any path where injected input changes whether rows come back has to be closed the same way. Parameterise it and the oracle disappears.

<Accordion title="Where the signal lives">
The message is the obvious tell, but the response length moves with it, and length is easier to sort on. In Intruder I grep-match `Welcome back` instead of reading bodies by eye. One row keeps the string and the rest lose it. If the two states ever look identical, the condition is not actually reaching the query.
